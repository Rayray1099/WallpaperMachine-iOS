# iOS export and AirCard boundary

Export is separate from foreground playback. `WallpaperExportService` decodes real video frames with AVFoundation, composites placement/aspect/zoom, and writes H.264/HEVC MP4, PNG/JPEG frame sequences (optionally ZIP), or an experimental PosterBoard `.tendies` ZIP. Image sources are explicitly still images. The export sheet supplies a visible local-WebKit frame provider for web sources; callers can still inject their own provider. The installed scene build uses an injected live `WallpaperFrameProvider`; absent a provider the operation fails rather than substituting an author preview. The pending fixed-step replacement described below is implemented in source but has not passed Apple compilation, GPU execution or device export.

Independent actual-file validation passed all frame decodes/CRCs and sampled source fidelity; Safari completed the 840,285,420-byte download and AirCard imported the named full-quality file. ## References and provenance

- [22amiibo/mp4To.Tendies](https://github.com/22amiibo/mp4To.Tendies) demonstrates JPEG frame assets, CAML and plist structure inside a ZIP renamed `.tendies`. Its defaults are iPhone-oriented. It was inspected as a format reference; no external template wallpaper imagery is bundled.
- [Mak5er/AirCard-iOS](https://github.com/Mak5er/AirCard-iOS), specifically `ios-app/TendiesEngine.swift`, imports `.tendies` as ZIP, discovers descriptors and images, and distinguishes container/database payloads. WallpaperMachine exports collections-style assets, not a system database container.
- The export source includes generated keyed archive metadata and CAML from field values. Compatibility is experimental until an actual exported archive is imported and checked on this user's iPadOS version. Generated metadata is not proof of operating-system acceptance.

### Modern package layout is independent of FPS

`TendiesPackageLayout.posterBoard27` is an **opt-in compatibility experiment**;
the native exporter and PC server still default to `legacy`. The browser and
native paired-PC conversion sheet expose this layout as an explicit experimental
selection. HTTP/Python use `package_layout`; both local converter CLIs accept
`--package-layout posterBoard27`. The server forwards the selection to the Swift
frame packager's `packageLayout` request field, and completed-job receipts preserve
it across restarts. Native download receipts report the requested layout, not an
independent inspection of the downloaded package. The
new layout generates all three published logical-point planes, stock-shaped
numeric bundle/asset names, aligned descriptor/userInfo references and the two
PosterKit configuration archives together. Empty Floating/Foreground planes are
transparent; they do not invent depth segmentation. Background `resizeAspectFill`
fits the original bitmap to the logical canvas without resizing or recompressing
the JPEG asset. Pixel dimensions, frame count, contents-keyframe encoding and
duration remain independent of the package layout.

This is **not a lazy decoder or a fix for the measured startup watchdog**. The
contents-keyframe list still references every frame. `imageSequence` is rejected
for the new layout rather than claiming an unverified private consumer. Keep a
separate archive identity when comparing layouts; never rewrite an installed
descriptor, discard existing wallpapers or infer successful installation from
an import/thumbnail. Package tests establish structure, not system playback.

### Current keyed-archive format repair candidate

The current uncommitted export repair keeps the explicit XML compatibility path
in `KeyedArchiveBuilder`, while production `providerInfo.plist`, optional
`otherMetadata.plist`, and Collections suggestion metadata are emitted as binary
keyed archives. The binary path round-trips the XML `CF$UID` spelling through
Foundation before binary serialization so references become real plist UID
objects. The suggestion graph keeps the stock `Collections`
`displayNameLocalizationKey`, the user title in `localizedDisplayName`, the
numeric `<id>.DYNAMIC` descriptor identifier, and an independent gallery UUID.

This is a **format-correctness candidate**, not an established picker or playback
repair. The scoped fixture checks validate binary headers, UID bounds, class/object
graphs and identity relationships. The macOS iOS-build workflow runs the same
test before the full ARM64 build so its Darwin-only `NSKeyedUnarchiver` proxy
checks execute. A passing archive/decoder check still does not establish private
PosterBoard acceptance, picker visibility, animation, looping, orientation or
lock/unlock behavior. Missing suggestion metadata remains a device-side
hypothesis rather than a proven root cause.

The default exporter still generates the legacy `Chip` / `LayeredAnimation` layout with pixel-space CAML. [GoldenNugget's pinned modern-layout converter](https://github.com/GoldenNugget-Team/GoldenNugget-mobile/blob/4e6a595d9fdce5e0a925d572c581f361b6664b54/Nugget/Core/PosterBoardConverter.swift) instead publishes named plane roots, uses logical-screen document units, adds a Foreground plane and rendering/configurable-options archives, and synchronizes Clownfish bundle/plane names with metadata. Its source describes both Depth support and safeguards against renderer traps. These are third-party migration rules, not Apple specifications or proof that every legacy archive fails.

Reducing FPS changes none of those package-layout fields. A loading spinner therefore cannot establish either excessive frame count or a layout fault. The opt-in mode is not a validated system repair. Do not switch only the family, rename one bundle, fabricate configuration metadata, or reset installed descriptors to imitate this migration; actual system validation remains required. Preserve the approved short legacy diagnostic as a separate control, rather than rewriting it into another format.

Both the output pixel size and PosterBoard screen class remain explicit. The target's observed logical geometry is 834×1210 points at2x (1668×2420 portrait pixels). ## Timing and limits

Video export uses source timestamps. `MediaCaptureFrameProvider` adapts actual live surface snapshots but cannot guarantee deterministic web/scene time: WebKit snapshots are asynchronous and arbitrary webpage clocks are not seekable. It must not be described as an offline deterministic scene renderer or guaranteed 60 FPS capture. The visible local-WebKit export host remains outside recycled Form rows and must be attached, loaded and laid out. Web export requests at most 30 FPS and downscales captured images into a 1920-pixel edge bound (WebKit may first allocate its full viewport snapshot). Output size is independent of that capture bound. The provider is prepared once by the export service; the live clock starts on the first requested frame and is reset between exports. Capture is checked both before and after each snapshot, including the final frame: more than 0.5 seconds of timeline drift fails instead of silently time-compressing slow captures. Rewinding/repeated timestamps and nonfinite/invalid dimensions are rejected. Readiness and each snapshot have separate 10-second timeouts; cancellation stops awaiting an uncancellable WebKit callback and discards its late result. No microphone adapter is started by export, and preview updates retain the selected capture FPS with audio response disabled. The page's capture surface is the visible preview viewport, scaled into the chosen output; arbitrary JavaScript/WebGL clocks are not seeked. The installed native scene provider uses this same conservative live-clock boundary; Your Name's 60-FPS attempt failed it rather than silently reducing quality.

Movie reader initialization/start/copy failures retain bounded diagnostics: fixed failure stage and reader status plus allowlisted NSError domains and numeric codes, with at most two underlying errors. Arbitrary domain strings, localized error descriptions, paths, URLs and other userInfo text are not forwarded by those failure paths. This is diagnostic instrumentation, not a decoder or memory fix.

Copy-stage diagnostics also include reader-call attempts, successful source
samples, the requesting output index and its rational target time. Lookahead may
fail before that output tick is written; the counters are not completed output
frames. Movie-to-tendies export now keeps decode, composition and append inside
one synchronous per-frame autorelease pool. Other providers retain their async
path. Video previews pause while the export sheet is open and resume on dismissal.
This is a candidate ownership/concurrency correction, not proof that pooling alone
fixes total memory growth or the physical device's `-11819` reset.

Current movie export does not mux audio. Standalone WebM input is rejected accurately by the media layer pending connection to the existing native WebM reader. iOS app background suspension can interrupt an export; the operation must report cancellation/failure, not success with an incomplete file.

## Pending fixed-step native scene export

The source replacement creates a dedicated attached native handle, enables an immutable manual frame rate before initialization, waits for compiled-graph readiness (not a fake presented frame), and requests sequential indices `0...17999`. Simulation time is `index/fps`, with zero advance for index zero and `1/fps` thereafter, set before shader, particle and runtime updates. Ordinary draw timers and the poster mailbox do not advance this handle. Each request copies the owned scene composition through the same GPU command buffer and publishes private context/index/FPS-tagged completion. Swift primes index zero once and consumes its cached buffer at the first output time; it never requests N+1 ticks for N output frames. Encoding can be slower than real time without reducing the selected FPS or native resolution.

This is a separate capability, **not a relaxed live drift budget**. Video textures, scripts and pending text layout are rejected generically. Input is fixed, audio/media response is disabled, and later source/settings/surface changes end the immutable session. Cancellation/teardown invalidate the mailbox, fail pending native requests and drain renderer ownership before releasing the shared-assets lease. Failure reporting preserves a specific native shader/surface/GPU diagnosis before using a generic manual-export failure; status `-1` alone is not mislabeled as an unsupported feature. Per-frame synchronous JPEG/ZIP work has its own autorelease pool; that does **not** establish a whole-pipeline memory ceiling or fix the unresolved AVFoundation reset.

Local verification passed 155 portable iOS script tests (including the opt-in tiny real FFmpeg/Swift conversions), Swift syntax parsing, and a release-mode C++ contract with all 18,000 indices plus 100 completion/failure races. **Required but not executed:** 53 actual Apple provider/compositor/JPEG tests, 25 UIKit recorder tests, actual C ABI/Metal compilation, the eight-tick-per-run fast/slow native GPU regression, then the full 480-frame Your Name iPad export and independent archive/system-playback checks. GitHub refused the prior full-build and native jobs before any steps ran because of account payment/spending-limit restrictions. No pending renderer was installed; missing jobs are not source test failures or passes. No Wallpaper Engine reference-frame comparison was performed.

## Installation safety

The share sheet can pass an archive to compatible AirCard versions. No direct AirCard exploit, respring, wallpaper database replacement, or system write is performed by this app. Importing/previewing a file in AirCard is distinct from authorizing its application to the system wallpaper store. Never infer continuous Home/Lock Screen playback from an in-app loop.

### Concrete compatibility gates before Flash

Source review of AirCard-iOS checkout `40640c4d` shows that import discovers descriptor folders and decodes a JPEG thumbnail; it does not render the CAML, validate animation geometry/timing or prove PosterBoard accepts the metadata. WallpaperMachine's default contents-keyframe wrapper previously omitted its position: under standard Core Animation defaults, that translated all frames by negative half their width/height. The generator now explicitly centres both the wrapper and image layer, retaining the root's explicit zero anchor/position. Portable regression checks generate portrait and landscape manifests for 1, 60 and 301 frames and compose the layer transforms; this is not an OS renderer test. Archives exported before this correction are not corrected retroactively. A rebuilt `326dd9d1` app has now generated a new archive that passed the 75 actual-content checks below; OS runtime acceptance remains separate.

Additional unresolved source-comparison boundaries:

- `834w-1210h@2x~ipad` is the device screen class, not the 1080×1920 JPEG canvas. The generated index uses the actual JPEG dimensions and requests fit scaling. A 1080×1920 canvas fitted into 1668×2420 leaves approximately 153 pixels of side margin; private PosterBoard scaling/cropping still needs an actual four-corner test. A native 1668×2420 synthetic export removes this aspect mismatch for the first geometry test.
- Default contents animation preserves the reference's `calculationMode="linear"` and omits explicit `keyTimes`. It declares duration as frame count/FPS; exact discrete frame holds and loop-seam cadence have not been verified. With 60 values over two seconds, evenly distributed endpoints span 59 intervals, not 60 one-thirtieth-second holds. Do not claim exact 30 FPS OS playback from successful archive generation.
- AirCard's Flash identifier rewrite updates the descriptor ID, userInfo ID and top-level Wallpaper.plist ID but does not update `assets.lockAndHome.default.identifier`. Different values are **not a proven broken reference**: Placard's equivalent `LayeredAnimation`/`Chip`/2.01 video writer deliberately uses a random installation ID and nested asset ID `9183`, and Nugget explicitly rewrites only the top-level Wallpaper ID. These public producer patterns suggest distinct ID roles, not an Apple consumer guarantee. Do not fabricate suggestion metadata or recursively rewrite nested identifiers to force equality. The installed AirCard executable and private OS consumption remain separately unverified.
- Provider-info and display-name keyed archives match Poster-Lab's XML object graph; import name/thumbnail acceptance is not a private-class unarchive/render test. The alternate plist `ImageSequence` encoding is unchanged and is not validated by the default-encoding checks.

The reviewed AirCard Flash path is broader than copying a file: it injects a new descriptor into legacy and, on iOS 18+, modern Collections extension stores, writes a replacement `com.apple.PosterBoard.unprotectedUserDefaults.plist` into PosterBoard preferences and attempts the same global mobile-preference write, then automatically triggers NeoSpring. Its `resetProtections` parameter does not guard those preference writes, and the modern/global writes can fail silently. No matching app-level backup/rollback workflow was found. These are source observations, not a binary audit of the installed AirCard version.

Before any separately authorised Flash, retain/recheck the independently validated **new actual synthetic archive** (ZIP CRC, exact frame set/JPEG dimensions, XML/plist graphs, asset references and four-corner coordinates), preserve actual asset references through the external installation-ID rewrite, and check the installed AirCard/iPadOS write behaviour. The user must explicitly approve the descriptor/preference writes and automatic respring, retain a known-good wallpaper through system UI, arrange an up-to-date user-controlled device backup and recovery access, and accept that selecting the old wallpaper is only a visual fallback—not reversal of injected descriptors or overwritten preferences. Any low-level baseline capture, restoration or deletion needs its own explicit authorisation and a verified method; do not read private wallpapers or promise automatic rollback. After a permitted Flash, picker presence, selection, all four corners, a full loop/seam, lock/unlock, orientation and recovery to the known-good wallpaper remain separate runtime gates.
